# patrickserrano.com / patrickpowers.dev

Personal site and blog, served from two domains:
[patrickserrano.com](https://patrickserrano.com) and
[patrickpowers.dev](https://patrickpowers.dev).

Built with **Next.js** (App Router), **Tailwind CSS v4**, and **shadcn/ui**,
themed to a dark monospace look. Deployed on **Vercel**.

## Two domains, one deployment

A name change is in progress, so both domains are live and serve identical
content apart from the surname — "Patrick Serrano" on one, "Patrick Powers" on
the other. A single Vercel project has both domains attached; the variant is
picked per request from the `Host` header in `src/lib/site-server.ts`.

Consequences worth knowing:

- **Every route is server-rendered on demand.** Reading `headers()` opts the
  whole tree out of static prerendering. That is the accepted cost of one
  deployment; the pages are small and Vercel caches at the edge.
- **Each domain canonicalises to itself**, via a per-request `metadataBase`,
  so both stay independently indexed rather than one being folded into the
  other.
- **Unknown hosts fall back to the Serrano variant** — Vercel preview URLs and
  `localhost` included.
- Contact address and social links are deliberately *not* varied. They stay on
  the old name until those accounts are themselves renamed.

## Develop

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # production build
npm run start    # serve the production build
npm run lint     # eslint
```

`localhost` resolves to the Serrano variant. To see the Powers variant, either
force it with `SITE_VARIANT=powers npm run dev`, or send the host directly:

```bash
curl -s -H 'Host: patrickpowers.dev' http://localhost:3000/ | grep -o 'Patrick [A-Za-z]*'
```

## Structure

- `src/app/` — routes: `/` (about), `/resume`, `/blog`, `/blog/[slug]`,
  plus generated `robots.txt` and `sitemap.xml`.
- `src/components/` — site header/footer and `ui/` (shadcn components).
- `src/lib/` — `site.ts` (isomorphic per-variant config), `site-server.ts`
  (host resolution and nav, server-only), `resume.ts` (resume data), `blog.ts`
  (MDX reading/parsing).
- `content/blog/*.mdx` — blog posts (frontmatter: `title`, `description`,
  `date`, optional `tags`, `draft`).
- `public/` — static assets and the IndexNow verification key.

## Writing a post

Add an `.mdx` file to `content/blog/`:

```mdx
---
title: "Post Title"
description: "One-line summary for SEO and the index."
date: "2026-06-13"
tags: ["optional"]
---

Body in MDX.
```

Set `draft: true` to keep a post out of production builds while keeping it
visible in `npm run dev`.

**The blog appears only once a post exists.** With `content/blog/` empty the
Blog nav link is hidden, `/blog` returns 404, and neither it nor any post URL
is listed in the sitemap. Adding the first `.mdx` file brings all three back
with no other change.

## SEO

`robots.txt` and `sitemap.xml` are generated by Next.js
(`src/app/robots.ts`, `src/app/sitemap.ts`) and are host-aware: each domain
advertises its own URLs and points at its own sitemap.

On push to `main`, the [IndexNow workflow](.github/workflows/indexnow.yml)
maps the changed source files to paths and submits them to Bing/Yandex once
per domain. A failure on one host does not suppress the other.

Google Search Console is verified per domain with a DNS TXT record, so
nothing in this repo carries a verification token. Both properties should have
`https://<domain>/sitemap.xml` submitted.
